# F-log 最小变体与同口径实测

2026-10-10。F-log 已实际实现并与 F/S 运行相同工作负载；没有因为文件方案的初版全文件写入就直接淘汰该类别。有效原始数据为 [`evidence/p2-file-variant-20261010-v2.json`](evidence/p2-file-variant-20261010-v2.json)，结果只支持本轮比较，不提前宣布赢家。

## 实现与提交含义

实现位于 `log_store.py`，公开入口保持 `initialize / snapshot / apply / close`，额外提供明确的 `recover_tail`。初始关系快照、SHA-256 链追加日志和提交水位共同构成权威：

| 文件 | 职责 | 可否丢弃后重建 |
| --- | --- | --- |
| `snapshot.json` | 初始关系快照及校验 | 否 |
| `journal.log` | 从初始快照之后的关系变更及前项校验链 | 否 |
| `head.json` | 已提交 revision、日志偏移、最后记录哈希、当前状态哈希 | 否；不能凭最后完整日志行猜测提交 |
| `lock` | POSIX flock 的固定锁对象 | 不存关系事实；活动进程存在时不可任意替换 |

没有持久化索引或结果缓存；没有把日志当成可丢弃的索引。一次修改在排他锁内读取与校验权威、执行 CAS 和共享图约束，然后追加并 fsync 日志，fsync 新水位文件，原子替换水位并 fsync 目录，最后才向调用者返回新 revision。成环、断链、重复边和过期版本在追加之前被拒绝。

提交水位发布后若目录 fsync 失败，返回 `CommitUncertainError`，要求重读；不能声称回滚，也不能自动重试旧 revision。初始化不会覆盖已有目录；目录或三份权威缺失时显式失败。

## 半写、损坏与恢复

- 日志超过水位偏移时，普通读取和写入均抛 `UncommittedTailError`，不会把它静默忽略成正常成功。
- 显式 `recover_tail()` 先完整校验已提交前缀和重放结果，再将超出水位的字节写入独立隔离文件并 fsync，最后截断未提交尾部并 fsync。
- 已提交日志被截短、校验链损坏、快照损坏或水位损坏时，读取和恢复都拒绝继续；不能用“取最后好的一行”来退回旧版本。
- 此协议以正常受控写入和可信持久化水位为前提。SHA-256 用于发现损坏，不是身份签名；不防止攻击者替换多份权威并重算哈希。

原生读取必须校验三份权威并重放日志。备份若将它产品化，需要在同一读锁内保存三份权威，不能只备份 `snapshot.json`；当前最小变体没有补充备份 CLI、压缩或日志轮换。

## 真实可靠性证据

定向测试：**18 passed in 1.51s，exit 0**；完整实验 exit `0`。命令和计数见 [`evidence/p2-file-variant-validation.json`](evidence/p2-file-variant-validation.json)。

| 场景 | 实际结果 |
| --- | --- |
| 16 独立进程同 revision CAS | 1 提交、15 冲突；完整快照等于独立构造的赢家快照 |
| 已确认 revision=2 后，写下一条记录到一半再 SIGKILL | exit=-9；读取明确报未提交尾部；隔离 157 字节后恢复 revision=2 |
| 已确认 revision=2 后，完整追加但尚未发布水位时 SIGKILL | exit=-9；读取明确报未提交尾部；隔离 315 字节后恢复 revision=2 |
| 新水位持久化返回后 SIGKILL | exit=-9；直接恢复 revision=3，无尾部恢复动作 |
| 已提交日志改字节 / 截短、head 损坏、snapshot 损坏 | 4 类都拒绝读取与尾部恢复，损坏文件保持原样 |
| 发布水位后目录 fsync 报错 | 明确返回提交不确定；重新读取看到已发布 revision；旧 CAS 重试被拒绝 |

三个强杀场景都在恢复后继续成功更新。它们证明受测进程故障路径保留此前已确认提交；并未模拟系统断电、设备缓存丢失或任意文件系统故障。

## 比较口径

- 规模为 1 / 100 / 1000 节点，同一固定四叉树、同一节点定位变更、同样排序的返回字段。
- `read_mostly`：每独立实例修改一次，再窄/全各读 5 次、重新打开并完整读取一次。
- `continuous_updates`：每独立实例连续修改 20 次，再窄/全各读 5 次、重新打开并完整读取一次。
- 每格 **6 个独立实例轮次**，三候选各占据两次首位、两次中位和两次末位；初始化单独计时。
- 合计 18 格、108 个独立轮次、1134 次修改、1080 次原生读取、108 次重新打开；全部与独立编号 oracle 和明确 revision 预期一致。
- F/S 复用已有原生读取适配器；F-log 每读进行校验链和日志重放。重新打开对三者统一调用完整 `snapshot()`。
- 原始记录包含每次 wall、CPU、进程累计 RSS、OS 计数、min/median/max、运行顺序及实际持久化载荷；没有清 OS 缓存，不宣称冷启动、每请求净内存或 p95。

## 写入量与额外成本

1000 节点定位变更时，F 重新序列化约 `161962–161963` 字节；F-log 每次追加 `315–316` 字节日志并发布 `388–390` 字节水位；S 更新 2 行，提交后 WAL 为 `8272` 字节。这些是不同格式的应用/日志载荷，不是物理 SSD 写入或寿命指标。

F-log 初始快照使用紧凑 JSON，F 使用缩进 JSON，所以初始占用差异还包含编码格式影响；不能把全部空间差都归功于日志结构。F-log 在 1000 节点、20 次修改后权威总计约 `108769` 字节，日志仍会随修改次数增长。

追加写减少了载荷，但没有把整个修改变成 O(1)：当前仍需读取初始快照、重放日志、执行全图约束和计算当前状态哈希。最小实现没有压缩、分片或可重建内存索引；它们是后续工程成本，不能假装已经实现。

## 结论边界

这次补充证明文件类别存在可运行的日志变体，并能在明确提交水位下保留已确认提交、处理未提交尾部。代价是多份权威必须一致、故障后可能需要显式恢复、隔离文件维护、日志增长和重放读取成本。当前结果没有支持把 F-log 当作所有场景的默认方案，也没有据此淘汰文件类别。

选择需要结合项目规模、读取范围、修改频率与可接受的恢复操作；本记录不提前定赢家。尚未覆盖系统断电、跨机器或网络文件系统、日志压缩轮换及产品集成。现有 F/S、稳定源码和安装版未由本任务修改。
