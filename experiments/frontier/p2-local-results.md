- 图数据为固定编号的 4 叉树。预期集合逐个根据编号反查祖先，不调用候选查询；单测另用字面量验证多父菱形去重和 related 不扩展。

## 可靠性结果

| 场景 | F | S | 实际核验 |
| --- | --- | --- | --- |
| 16 独立进程同时 CAS | 1 提交、15 冲突 | 1 提交、15 冲突 | 最终 revision=2，仅新增一个赢家节点 |
| 提交前真实 SIGKILL | 恢复 revision=1 | 恢复 revision=1 | 子进程 exit=-9，恢复内容与旧快照完全相同，随后还能更新 |
| 提交后真实 SIGKILL | 恢复 revision=2 | 恢复 revision=2 | 子进程 exit=-9，恢复内容与已提交快照完全相同，随后还能更新 |
| 活跃写者期间连续 5 次备份 | 5 次一致并可恢复 | 5 次一致并可恢复 | revision 与节点值构成的独立不变量成立，恢复等于备份快照 |
| 逻辑迁移往返 | F→S→F 通过 | S→F→S 通过 | 保留 revision=5，节点/关系完整哈希相同，原权威未改变 |

提交边界为：F 在 `os.replace` 前停驻，或完整 `_write` 已完成文件/目录 fsync 后停驻；S 在原生 `commit()` 前停驻，或其返回后停驻。父进程实际发送 `SIGKILL`，没有用 Python 异常冒充进程终止。

F 在提交前强杀后留下一个已经写好的孤立 `.tmp` 文件；原权威保持有效，也没有错误读取临时文件。此实现尚未自动清理孤立文件，需要产品化时定义安全清理规则。该现象保留在 JSON 的 `orphan_temporary_files`，不伪装成零残留。

F 备份在共享读锁内复制完整文件；S 使用标准库 SQLite backup API。两者恢复后都通过既有 Registry 的完整快照校验。备份时 F 捕获 revision `7/11/11/11/11`，S 捕获 `1/1/2/2/3`；这代表不同采集时点，不能比较成谁更“新”。两者写者最终都到 revision `31`。

迁移是明确的离线适配器：先导出快照，在新临时权威中初始化，再用目标后端的锁或事务保留导出 revision，校验后独占发布新路径。它不重放虚构更新、不覆盖目标、不双向同步；当前仅在实验脚本提供，没有扩展稳定 API。

## 原生查询对照

两者读取相同持久化图，返回同样的 revision、排序节点与范围内关系。每格先记录一次首次原生调用，再做 **5 次**计时；轮换 F/S 顺序。共 12 个候选/规模/范围组合、60 个重复样本和 12 个首次调用样本，全部与独立 oracle 一致。

F 在读锁内解码全 JSON，再用程序筛选；S 使用单读事务、索引和递归 CTE。两者计时前均完整校验数据；计时内都假定权威由有效写者维护，不重复完整 DAG 校验。没有结果缓存，没有把 JSON 原文交给 Agent。

下表为中位数毫秒，括号为实测 min–max；不是 p95，也不是冷缓存数据。

| 总节点 | 范围 / 返回节点 | F 文件扫描 | S 递归 CTE |
| ---: | --- | ---: | ---: |
| 1 | 窄 / 1 | 0.118（0.111–0.152） | 0.526（0.514–0.611） |
| 1 | 全 / 1 | 0.110（0.105–0.113） | 0.367（0.345–0.374） |
| 100 | 窄 / 4 | 0.322（0.299–0.392） | 0.611（0.581–1.065） |
| 100 | 全 / 100 | 0.387（0.372–0.420） | 1.166（1.152–1.527） |
| 1000 | 窄 / 4 | 2.019（2.000–2.037） | 0.879（0.861–0.893） |
| 1000 | 全 / 1000 | 2.906（2.870–2.944） | 10.578（10.481–10.670） |

在这组实现与数据下，F 的小规模和全量读取较快；S 在 1000 节点中局部读取约快 2.3 倍。全量查询必须返回 N 个节点，不能根据窄查询优势宣称总体成本不随规模增长。

原始样本同时记录 CPU、进程累计峰值 RSS、缺页与 OS block 计数、返回字节数和 SQLite query plan。RSS 是进程累计峰值，不是每次调用独占内存；OS block 计数不是设备实际 I/O 字节。未清除 OS 页缓存，机器也未作为专用性能实验机隔离，数据用于本地选型参考，不作为生产 SLO。

## 局部更新与写入量

每规模、每候选执行 5 次相同节点定位修改，CAS revision 和最终图都校验。耗时包含原有实现的全图读取/约束校验及持久化，未只计算单条 SQL。

| 总节点 | F 更新中位数 ms | S 更新中位数 ms | F 每次完整序列化字节 | S 提交后 WAL 字节 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.532 | 1.093 | 121 | 8272 |
| 100 | 4.780 | 3.514 | 16161 | 8272 |
| 1000 | 43.100 | 25.906 | 161961 | 8272 |

S 每次实际改变 2 行：节点及 meta revision。F 每次重写整个快照；1000 节点时，这个具体实现的写入负担较高。两列字节的含义不同，不能据此计算 SSD 物理写放大或寿命。日志/分片文件变体本轮未实现，因此没有据此淘汰整个文件方案类别；如选择 F 并出现频繁更新，应单列变体成本再测。

## 保留的失败和纠正

- 首轮两项备份测试误报失败：本机 Python 3.8 的 `time.monotonic()` 进程起点不同，实验跨进程比较时钟产生错误判定；备份内容本身一致。现改用 IPC 完成 Event 确认写者活动，跨进程时间仅用于记录。原证据见 [`p2-local-test-before-fix.json`](evidence/p2-local-test-before-fix.json)。
- 首轮查询包装层对 F 结果做了多余深拷贝，增加全量查询成本。移除后对全矩阵重跑，选型只使用 v2；首轮 [`p2-local-20261010.json`](evidence/p2-local-20261010.json) 保留，不删除或混合样本。

## 选型含义与剩余范围

本地单用户、关系较少且主要做全量汇总时，F 保持了可接受的简单实现和较低读取成本；需要较多局部查询或关系更新时，S 提供原生索引、事务和标准备份接口，在这组数据下更有优势。两者均有本轮进程级恢复证据，不能把“文件没有数据库事务”直接等同不可靠。

本子任务已无阻塞其已列场景的环境问题。仍未验证系统断电、设备缓存丢失、网络文件系统、跨机器事务，以及恶意绕过有效写入协议后原生局部查询的全局损坏检测。真实服务候选、真实 Agent 编排和产品集成由其他实验交付，不能拿本记录代替。离线迁移/原生查询仍是实验适配器，采用方案时需要独立集成和回归。
