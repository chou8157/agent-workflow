# 产品命名与已有项目升级核查

日期：2026-10-16。范围：当前已安装的原版与轻量试验版、发布安装器、项目结构升级和工作项数据兼容性。仅在临时项目写入验证数据，未修改运行源码、实际安装目录或业务项目。

## 明确结论

这是 agent-workflow 的迭代，长期应保留同一个产品名和调用入口。此前使用 agent-workflow-frontier 是为了并存试验、保护旧安装，并不意味着必须成为第二个产品。仓库名、源码 agent-workflow/、业务项目 .agent-workflow/ 和已有工作项均未整体改名。

已有项目不用重新初始化，也不需要删除历史数据或逐项目重装技能。当前结构版本 5 的项目已经可以直接由新脚本读取、追加活动和生成报告。但是，当前交付尚未完成旧技能原位更新、回滚和旧项目升级的完整路径；上一轮“可用”覆盖核心使用链路，不应延伸成“所有旧项目均可无缝升级”。

## 三种更新需要分开

| 层次 | 更新对象 | 当前结果 |
| --- | --- | --- |
| 技能程序 | Codex skills 内的脚本、模板和说明 | 只有独立新增安装、同包重试及完整性检查；没有原位更新或回滚 |
| 项目结构 | 各项目原有 .agent-workflow/ 和入口规则 | 保留现有内容，旧结构可计划补齐；发现一个迁移提醒处理缺陷 |
| 项目事实及关联 | 工作项状态、活动、节点关系 | v5 状态可直接增量记录；旧状态缺失须单独迁移；多项目关系按需接入 |

技能只需更新一份，各项目继续使用自己的原目录。必要的旧格式整理属于小范围数据迁移，不是重建项目。历史缺少业务日期不会因更新自动变成可靠周报。

## 本轮实测

使用当前原安装版生成一个 v5 项目和工作项，加入自定义入口内容，然后直接调用新安装版，未对项目重新运行初始化：

- 读取、结构检查和升级计划正常，原文件哈希未变。
- 在原工作项追加活动成功，不依赖节点身份或关系数据库；原状态字段保留。
- 同参数重试返回 unchanged，未生成重复活动。
- 新版更新任务状态后活动保留；旧版顺序更新状态也保留已知活动。
- 新版生成当前项目周汇总成功；AGENTS、工作流入口和公共状态的自定义内容不变。

另构造 v2 且已有工作项、没有 .state.json 的项目：

- 只读 plan 不写文件。
- 活动追加明确拒绝缺少状态文件。
- 单独 migration-check / migration-apply 可生成合法状态；旧正文保留，创建和完成日期未知继续保持未知，没有补造活动。
- apply-safe 本身暴露下述缺陷，不能据其 up_to_date=true 认定迁移完成。

## 升级前必须补齐的缺口

### 1. 发布安装器不支持连续升级

build_release.py:22 固定包名 agent-workflow-frontier 和版本 0.1.0；verify 只接受精确版本；install 目标固定，已有不同内容会拒绝覆盖。独立审查在临时 skills 目录实测：首次安装成功，同名不同合法内容被拒绝，下一版本清单被当前验包器拒绝。

因此不能通过改文件夹名字、改 SKILL 名称或重复 install 来完成可靠升级；当前也没有更新失败回滚流程。首次安装安全性与连续更新安全性是不同验收项。

### 2. 老项目结构升级错误处理迁移提醒

upgrade_workflow.py:114 将一整句迁移提示放入 suggestion；apply_safe_upgrade 在 :149 将其统一当文件路径写入。对 v2 且已有 work-items 的项目，会在命令当前目录创建名称为整句中文提示的文件。

同时结构版本被写为 5，重新生成计划时基于旧版本的迁移提醒消失；在本轮入口已含要求标记的用例中，返回 up_to_date=true，但工作项仍没有 .state.json。主 Agent 与独立审查分别复现。该问题继承自旧脚本，现有升级测试先删掉了 work-items，未覆盖此分支。

修复方向：把文档建议文件与需要执行的迁移动作分开；不按结构版本掩盖缺失状态、冲突或未完成迁移。“结构最新”和“工作项可用”分别检查，不能只改版本号就宣布全部完成。

### 3. 新旧写入器同时使用可能丢活动

原安装版 task_context 不遵守新写入锁。顺序操作保留活动并不等于可以并发混用。

本轮在临时副本做受控交错：实际旧版先读取状态，暂停写回；实际新版追加一条活动；再恢复旧版状态写回。活动数量由 1 变 2，再变回 1，新活动丢失。只注入执行交错时机，没有修改两份安装代码。

更新过程必须统一运行入口，并在切换前结束旧写入；回滚必须保留项目数据，不能把旧数据快照盖回当前工作项。当前分开技能名无法自动约束旧会话，文字约束不足以算完整升级保护。

### 4. 产品和版本的表达不连续

原产品 CHANGELOG 是 1.0.0，试验包是 0.1.0，两者 WORKFLOW_VERSION 均为 5。0.1.0 只是试验包版本，不应作为原产品重新从零发布的依据。

原入口 $agent-workflow 仍选择旧安装；独立包不修改项目入口。旧 AGENTS 模板本身没有固定安装路径，不能说所有项目都需要改路径。已知项目如有自定义硬编码路径则应在预检中提示。

## 最小整改方案

1. 产品和日常入口统一为 agent-workflow，frontier 留在实验分支和内部试验标识中。后续沿既有版本线发布预览版，具体版本待兼容边界冻结。不要为消除内部字符串而批量重命名既有节点身份文件和数据库路径。
2. 补轻量更新流程：检查当前安装及本地改动、预览更新内容、保留旧运行包、切换到新包、验包与最小运行核查、失败恢复旧运行包。不引入后台服务或通用包管理平台。
3. 加已有项目只读预检。v5 合法项目直接复用；旧格式仅处理缺失状态或明确需要补齐的结构；冲突和未知日期明确展示，不重建目录或覆盖文档。修复迁移提示缺陷。
4. 统一写入器和切换边界。多项目关联仍为可选，未接入项目不生成关系库；新增活动沿用本地收口。能力清单目前未统一登记活动/网络，后续按必要范围整合，避免同时维护两套有冲突的启用状态。

结构版本只表达项目文件与规则契约；如新增必须落地的规则或结构，再按项目约定升级 WORKFLOW_VERSION。产品包版本变化本身不意味着每个项目必须重建。

## 下一阶段验收门槛

- 当前 v5 项目保留任务、历史和自定义文档，直接开始新增活动。
- 较老结构、不完整状态和冲突分别识别，升级后不得假报已全部完成。
- 重复更新、升级中断、本地安装改动、失败恢复均有明确行为。
- 回退运行包不删除已新增的活动和关系；版本切换期间不允许新旧写入交错覆盖。
- 完成预检与最小验证后，再将独立试验入口收敛到原产品入口。
