## 日常用法

使用更新后的 `$agent-workflow`，可以直接说：

> 检查当前项目的工作流版本，告诉我需要补齐什么。

> 把当前项目已有的工作流升级到最新版，保留原文档和全部任务记录。

> 使用这个新版交付包更新 agent-workflow，先给出更新计划。

Agent 会处理版本识别、升级计划、必要的状态迁移和检查。多项目关联仍是可选能力；已有节点身份和关系库继续复用。只升级程序不会自动扫描或迁移其他项目。

## 已支持的升级

| 起点 | 处理方式 |
| --- | --- |
| 已有技能没有发行清单 | 识别为旧安装，完整保留运行文件备份后更新；不猜测旧产品版本 |
| 已有合法旧发行包 | 比较产品版本、绑定来源与当前安装指纹，再更新 |
| 项目没有结构版本标记 | 从历史入口识别实际文件，生成版本路径和缺口清单 |
| 项目结构 1、2、3、4、5 | 按增量计划升级到结构 6，保留已有内容 |
| 项目结构已为 6 | 仍检查状态和文件缺失，重复升级不重写已完成事实 |
| 未来版本、非法格式或事实冲突 | 明确列出问题并停止写入，保留原数据 |

“支持升级”包括识别冲突和协助处理，不代表所有有冲突的旧资料都能无人判断。旧版迁移后正文残留旧状态时，需审阅它与当前 `.state.json` 的关系；不会自动选择一个说法覆盖另一个。

## 数据保护

- 程序更新保留完整旧运行包，失败可恢复，成功后也可按事务回滚。
- 回滚程序不回退项目数据，不删除新增活动和关联；回退后仍要检查旧程序能否处理当前项目结构。
- 项目升级补缺，已有入口生成增量建议供审阅。结构最新、任务状态可用、文档已审阅分别显示。
- 历史创建或完成日期未知时继续保持未知，不用文件时间补造。
- 升级前结束旧写入，升级后统一使用当前版本；旧安装脚本和试验别名不能同时写同一工作项。
