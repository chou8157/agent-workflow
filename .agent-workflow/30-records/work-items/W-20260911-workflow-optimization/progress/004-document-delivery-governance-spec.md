# 004：内部文档与外部交付治理开发前规范

## 目标与边界

本规范只处理第二个问题：文档的生成、归属、存储、引用、生命周期和对外交付。第三个问题“按项目复杂度渐进生成结构”暂不进入本轮开发。

本规范是开发前基线。实现前必须由用户确认；确认前不得改模板、脚本、目录结构或迁移现有文档。

## 一、双平面模型

### 内部事实平面

内部文档服务于智能体协作、恢复上下文、审计和持续开发，允许使用工作项 ID、内部路径和内部引用。

逻辑类型：

1. `charter`：项目目标、范围、边界和术语。
2. `policy` / `contract`：规则、接口、状态机和验收契约。
3. `decision`：决策背景、选项、决定和后果；被替代时新增文档。
4. `work_item`：目标、范围、验收项和来源；生命周期由 `.state.json` 管理。
5. `status`：当前阶段、判断、风险、证据边界和下一步。
6. `knowledge`：稳定、可复用的指南和说明。
7. `evidence`：测试、验收、发布和审计证据；原始机器产物与可读摘要分离。
8. `scratch`：临时草稿、调研、实验和中间产物，必须隔离并有过期规则。

### 外部交付平面

外部文档是独立发布产品，不是内部 `progress` 的另一种文件，也不是内部文档的可变镜像。

逻辑类型：

- `weekly`：周报。
- `phase_report`：阶段报告。
- `delivery`：交付说明。
- `acceptance`：验收报告。
- `release`：发布说明。

外部文档必须脱离 `.agent-workflow/`、工作项 ID、内部路径和内部上下文独立阅读。

## 二、唯一权威来源

| 事实 | 唯一权威来源 |
| --- | --- |
| 工作项生命周期 | 工作项目录 `.state.json` |
| 工作项目标与验收 | `work-item.md` |
| 项目当前阶段 | 项目级 `current-status.md` 结构化区块及正文判断 |
| 决策内容 | `decision` 文档本身 |
| 稳定规则和契约 | `policy` / `contract` 文档本身 |
| 测试和验收事实 | `evidence` 及验证记录 |
| 内部可复用知识 | `knowledge` 文档 |
| 外部交付正文 | 已批准并发布的交付物版本 |
| 索引、报告、Memory 摘要 | 派生视图，不得成为事实源 |

同一事实只能有一个权威来源。其他文档只保存引用或摘要；冲突时检查工具报告冲突，不自动猜测覆盖。

## 三、元数据规范

### 内部文档最小元数据

- `doc_id`：稳定唯一标识。
- `doc_type`：逻辑类型白名单。
- `authority`：`canonical`、`derived` 或 `reference`。
- `status`：`draft`、`active`、`superseded`、`archived`。
- `created_at`、`updated_at`。
- `source_work_item`：可选来源工作项。
- `supersedes` / `superseded_by`：可选替代关系。
- `retention`：证据和临时文档可选保留策略。

机器字段不得在正文中重复维护。保留 front matter 时，不得再建立一份可独立编辑且含相同字段的中心注册表。

### 外部交付物最小元数据

- `artifact_id`：交付主题或周期的稳定标识。
- `artifact_type`：`weekly`、`phase_report`、`delivery`、`acceptance` 或 `release`。
- `audience`：目标读者。
- `period`：报告或交付覆盖范围。
- `version`：发布版本。
- `status`：`draft`、`review`、`approved`、`published`、`superseded`、`withdrawn` 或 `archived`。
- `created_at`、`approved_at`、`published_at`。
- `classification`：对外公开范围。
- `supersedes`：被替代的交付物版本。

内部单独保存 `provenance manifest`，记录输入文档、状态快照、内容哈希、生成命令、审查结果和批准信息；这些内部追溯信息不进入外部正文。

## 四、生命周期

### 内部文档

```text
draft -> active -> superseded -> archived
```

- `decision` 被替代时新增决策，不原地改写已接受的历史决定。
- `evidence` 采用追加记录，错误通过更正记录处理。
- `status` 允许更新，但不能成为历史事实唯一来源。
- `scratch` 必须有 TTL；到期后晋级、归档或清理，不能默认进入 Memory。

### 外部交付物

```text
draft -> review -> approved -> published -> superseded / withdrawn / archived
```

- `draft` 可重新生成。
- `review` 执行事实、边界和格式检查。
- `approved` 固定待发布快照和批准信息。
- `published` 禁止原地覆盖；修订必须产生新版本并设置 `supersedes`。
- `withdrawn` 必须记录原因和时间，不能静默删除。
- PDF、Word 等格式只是由已发布 Markdown 母版派生的输出。

## 五、外部文档发布流程

```text
显式选择事实范围
-> 固定 source snapshot
-> 生成 staging 草稿
-> 事实完整性检查
-> 内部引用/路径检查
-> 未确认判断检查
-> 敏感信息检查
-> 格式和独立可读性检查
-> 审阅与批准
-> 固化 published 版本
-> 归档、替代或撤回
```

生成时必须明确报告类型、时间范围、工作项/项目范围和目标读者；禁止扫描整个内部目录后随机拼接。

发布门禁必须拒绝：

- `.agent-workflow/`、内部文件路径和内部工作项 ID；
- 需要读者访问内部文档才能理解的引用；
- `待确认`、`可能`、`未验证` 等未确认判断；
- token、密码、手机号等敏感信息；
- 缺少报告周期、目标读者、来源快照或批准信息的文档。

## 六、五个角色的职责

### Skill

定义类型白名单、元数据 schema、内部/外部边界、生命周期和命令语义；禁止智能体自行发明文档类别或绕过发布门。

### 模板生成器

按文档类型生成最小模板；内部草稿、外部 staging 和已发布文档必须分区；不生成无归属、无类型或未声明来源的中间态正式文档。

### 工作流规范

规定创建、更新、晋级、审阅、批准、发布、替代、撤回和归档的时机与门禁；明确普通记录不等于对外交付。

### Memory

只索引 active 的章程、规范、已接受决策、稳定知识和已发布交付物索引；排除 scratch、未批准草稿、原始证据和过期版本；外部交付物不得反向覆盖内部事实。

### 工作项管理器

管理工作项生命周期和验收证据；生成外部文档前固定 source snapshot（输入清单、状态快照和内容哈希），不直接把实时目录扫描结果当作稳定报告输入。

### 检查/升级工具

检查文档类型、唯一 ID、权威冲突、引用闭包、生命周期、TTL、机器产物、外部泄露和发布版本完整性；升级时只迁移可证明等价字段，冲突和归属不明时停止并报告。

## 七、Git 与外部依赖边界

工作流不依赖 Git 才能运行。没有 Git 时，文件、元数据、状态文件、哈希和检查工具仍然提供治理能力；有 Git 时增加版本比较、审阅、回滚和协作审计能力。不得要求创建分支、worktree、提交或远端仓库作为普通文档操作前提。

不引入外部数据库、实时事件总线或全量事件溯源。后续如确有审计需求，只将关键生命周期事实追加为可选事件，并由事件生成只读索引。

## 八、开发验收标准

正式开发完成后至少验证：

1. 六个角色均使用同一类型和元数据规则。
2. 内部文档和外部交付物不会互相混入。
3. 外部文档按显式范围生成，不扫描整个内部目录。
4. 发布门禁能拦截内部路径、内部 ID、敏感信息和未确认判断。
5. 已发布版本不会因内部输入变化而自动变化。
6. 修订、替代、撤回和归档均保留关系与审计信息。
7. 无 Git 项目仍可完成生成、检查、批准和发布。
8. 迁移和升级不会静默覆盖或伪造历史事实。

## 当前决策

本规范完成开发前准备，尚未进入实现。用户确认后，按“规范与 schema -> 模板 -> 生成/发布命令 -> 检查门禁 -> 当前项目试用”的顺序开发；三个外部案例保持只读。
