# 第一阶段：状态同步问题分析

## 目标

确认工作项状态不同步的实际原因，区分唯一状态源、当前摘要和项目总状态的职责，为后续最小改造方案提供依据。

## 已确认事实

- `agent-workflow/scripts/task_context.py` 的 `set_status()` 只修改目标工作项 `work-item.md` 的第一处状态字段。
- `task_context.py` 不更新目标工作项的 `current-status.md`，也不更新项目根 `30-records/current-status.md`。
- `list` 和 `show` 读取的机器状态来自 `work-item.md`，因此可能与人工维护的摘要文字不一致。
- `FeedbackServer` 案例中，`W-20260910-customer-ai-dify/work-item.md` 为 `in_progress`，其 `current-status.md` 同时写有“正在进行：无”，已形成可复现的状态表述冲突。
- 当前项目已有 `W-20260911-workflow-optimization`，状态为 `in_progress`，作为本轮优化的恢复入口。

## 初步判断

- 机器状态应有单一事实源；当前摘要和项目总状态属于派生/解释信息，不应与机器状态平行维护而无检查。
- “用户说完成了”目前没有强制收口动作，状态更新依赖智能体是否记得调用脚本并同步摘要。
- 第一阶段应优先增加状态一致性检查和收口流程，不先自动改写自由文本摘要。

## 未完成

- 项目级状态区块与工作项状态的自动校验仍可在后续迭代增强。

## 实现结果

- 每个工作项目录新增 `.state.json`，记录生命周期状态、关系和时间字段；新建工作项自动生成。
- `task_context.py` 的列表、查看和状态更新优先读取状态文件；状态更新采用原子 JSON 写入，不再修改 `work-item.md`。
- 状态更新增加显式转换约束，归档状态不可重新打开；完成项允许重新进入进行中，以支持纠错和后续迭代。
- `migration-check` 只读报告缺少状态文件的旧工作项；`migration-apply` 仅为旧状态、标题和类型均有效的工作项生成状态文件，不覆盖已有状态。
- 工作项模板已明确状态文件与人类上下文的职责边界；项目级 `current-status.md` 增加独立的结构化项目状态区块。

## 验证结果

- 项目测试：`11 passed`。
- 脚本编译、工作流结构自检和 skill 格式校验通过。
- 当前项目 3 个工作项已完成状态文件迁移；迁移后检查无缺失项。
- 三个外部案例仅执行只读 `migration-check`，分别发现 2、20、2 个缺少状态文件的工作项，未修改案例文件。

## 五角色贯通

- Skill 入口和 `use`、`record`、`check`、`upgrade` reference 已统一指向 `.state.json` 和迁移流程。
- 模板生成器已生成状态文件和项目结构化状态区块。
- 项目 Memory 结构文档已登记状态文件、字段和状态转换。
- 工作项管理器已支持创建、读取、状态转换、阻塞原因、迁移检查和安全迁移。
- 自检工具检查状态文件和项目状态区块；升级工具将状态迁移列为版本 3 的审阅动作。
