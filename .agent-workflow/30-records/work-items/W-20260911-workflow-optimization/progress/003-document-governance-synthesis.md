# 003：文档治理现状与目标模型收敛

## 分析范围

本次对当前 `agent-workflow` 项目及三个只读案例进行文档盘点，并独立设计目标治理模型。未修改案例项目，未执行迁移。

## 已确认的现状

- `00-core`、`10-project`、`15-modules`、`20-gates` 和 `30-records` 已有基本职责划分。
- 工作项、当前状态、进展记录、验证记录和变更记录已有初步分工。
- 三个案例的工作项普遍存在旧状态字段或缺少 `.state.json` 的历史遗留问题。
- `progress` 中混有调研、实验、快照、草案和阶段结论。
- `requirements`、ADR/决策类文档和业务专项文档在不同项目中的归属不一致。
- `support-service` 的工作流目录中发现 `db`、`pyc`、`sha256` 等机器产物，说明证据与生成物边界不足。

## 目标模型

文档按用途划分为八种逻辑类型，目录可以按项目规模渐进启用：

1. 项目章程：目标、边界、术语和非目标。
2. 决策记录：背景、选项、决定和后果；被替代时新增记录，不改写历史决定。
3. 规范/契约：当前有效的行为、接口、状态机和验收规则。
4. 工作项：任务目标、范围、验收和引用；生命周期由 `.state.json` 管理。
5. 状态/报告：当前阶段、风险、证据边界和下一步，可覆盖更新。
6. 知识/指南：稳定且可复用的说明，不收录未经确认的中间结论。
7. 记录/证据：试验、发布、审计和会议等追加式记录；机器产物单独隔离。
8. 临时草稿：默认不进入正式结构，必须晋级为上述类型或过期清理。

## 唯一推荐原则

- 每个可验证事实只有一个权威来源，其他文档只引用，不复制机器事实。
- 文档必须有类型、唯一 ID、生命周期状态、来源工作项和更新时间等元数据。
- `Record` 追加写入，`ADR` 被替代时新增记录，`Status` 维护当前快照，`Work Item` 只描述任务。
- 检查工具报告孤儿文档、重复权威、缺失元数据、过期文档、断链和机器产物；语义冲突停止并要求人工决策。
- 小项目只启用 `Work Item + Status + Record`，有架构选择再启用 ADR，有稳定接口再启用规范，有复用需求再启用知识文档。

## 现状到目标的初步映射

| 现有内容 | 目标类型 | 初步动作 |
| --- | --- | --- |
| `AGENTS.md`、`SKILL.md`、`00-core` | 规范/工作流规则 | 保留，补充类型和引用边界 |
| `10-project`、`15-modules` | 项目章程/知识指南 | 按稳定事实和可复用知识拆分 |
| `work-item.md`、`.state.json` | 工作项 | 保留，禁止正文重复生命周期状态 |
| `current-status.md` | 状态/报告 | 保留为当前快照，不承担历史事实 |
| `progress`、`validation-log`、`changes` | 记录/证据 | 按事件和阶段整理，追加式保存 |
| `requirements`、业务专项文档 | 待映射 | 逐份判断是规范、决策、工作项还是知识 |
| `evidence` 下的 JSON/JSONL | 记录/证据 | 保留可复核证据，绑定来源工作项 |
| `db`、`pyc`、`sha256` 等机器产物 | 临时/生成物 | 移出正式工作流目录或隔离并默认忽略 |

## 实施边界

当前不执行批量重命名、删除、迁移或模板改造。下一阶段先建立文档元数据最小规范和映射清单，再选择当前项目中的少量文档做试迁移；外部案例继续只读。

## 待确认事项

- 哪些文档由人维护，哪些由脚本生成。
- 证据和机器产物的保留期限及敏感信息边界。
- 被替代文档的归档位置和删除授权。
- 是否需要将目标模型落为统一目录，还是只采用逻辑类型和元数据。
