# agent-workflow 发布与升级改进方案

日期：2026-11-25。状态：第一批发布与版本治理本地开发、验证及候选准备已完成，等待审阅；后续升级入口与迁移引擎仍为规划。

方案初始依据：仓库 `ff9ee6f` 的源码、文档和已有主线切换记录。最初分析仅核对实现与本项目升级计划，没有查询远端 Release 列表。后续第一批开发的新验证记录见工作项 `W-20261125-release-governance`，历史测试结果不替代新增能力的验收结果。

## 1. 目标与建议

让维护者能够按规则发布，让使用者通过一次清晰的升级请求完成适用更新，并知道更新了什么、是否完成、发生问题如何恢复。

建议分两轮交付：

- **1.1.0：收口已验证的功能，建立正式发布流程和公开文档。** 不为转正式而重新设计项目结构，也不把新的升级引擎混入已验证功能。
- **1.2.0 预览系列：改进安装更新、项目迁移、文档合并和完成状态。** 经真实项目副本及有限范围试用验证后，再发布 1.2.0。

版本号是拟议的迭代边界，不是已经发布的版本，也不代表已经承诺发布日期。如果 1.1.0 准备过程中发现运行行为需要较大修改，应先增加 1.1.0 的预览验证轮次。

保留产品名 `agent-workflow`、日常调用 `$agent-workflow` 和项目目录 `.agent-workflow/`。保留现有文件完整性校验、指纹绑定、备份和冲突保护，并在其上补齐使用流程。

## 2. 问题清单与优先级

P0 为正式发布前需要解决或明确的事项；P1 为升级体验迭代的核心；P2 为核心流程稳定后的维护改进。

| 问题 | 当前实现或已确认现象 | 改进方向 | 优先级 |
| --- | --- | --- | --- |
| 实验版、主线、正式版容易混淆 | main 已采用 1.1.0-beta.1；合并主线没有自动产生 1.1.0 正式发行包 | 明确合并、构建、发布和安装是不同事件 | P0 |
| v5 与产品版本混淆 | 旧主线产品为 1.0.0、结构为 v5；当前包产品为 1.1.0-beta.1、结构为 v6 | 产品版本与结构版本各自承担一种职责 | P0 |
| 改版本涉及多处手工同步 | 产品版本硬编码于构建脚本，说明和测试另有版本字面量 | 单一版本输入、生成发行信息、校验必要引用 | P0 |
| 公共文档包含内部过程 | README 包含主线切换、本机安装核验和备份记录 | README 面向使用者，内部证据保留在开发记录 | P0 |
| 运行包来源不直观 | 完整发行包由基础目录和 experiments/frontier 组合构建 | 先固定唯一构建入口，后单独收拢生产源码 | P0 / P2 |
| 获取新版与更新安装断开 | 更新器需要已经解压的本地包，无远端发现和下载 | 增加稳定版/预览版选择及本地包入口 | P1 |
| 项目升级需要人工串接 | plan、apply-safe、建议合并、status、结构检查分散 | 增加统一编排入口，保留已有底层命令 | P1 |
| 已有规则文档难以更新 | 主要补缺，既有文档按少数关键词和标记生成建议 | 管理模板基线、文件归属和受管理区块 | P1 |
| 成功状态容易误读 | 结构可已为 v6，但文档仍待审；退出码主要反映是否有阻断 | 定义整体结果、分项状态和明确的机器接口 | P1 |
| 迁移路径与执行步骤不完全对应 | 显示逐版本路径，实际主要对照目标模板补缺和统一迁移旧状态 | 建立显式迁移步骤和检查点，复用历史适配器 | P1 |
| 安装与项目恢复能力不同 | 安装有事务备份；项目升级主要依赖原子写入与重跑 | 为项目迁移增加受限写集、日志、备份和恢复 | P1 |
| 持续维护缺少自动门禁 | 当前没有受 Git 管理的 .github 工作流 | 建立版本、构建、升级、文档和发行一致性检查 | P0 / P1 |

这些问题不意味着现有工具不可用。当前已有实际使用和自动化验证基础，需要补齐的是持续演进时的一致性和完整操作流程。

## 3. 版本、渠道和兼容规则

### 3.1 两类公开版本

| 标识 | 负责什么 | 何时变化 |
| --- | --- | --- |
| 产品版本，如 1.1.0 | 用户安装的工具及其功能、修复 | 每次发布新的发行内容 |
| 工作流结构版本，如 6 | 项目数据、入口和强制规则协议 | 项目格式、入口路由或强制规则需要迁移时 |

Git 提交、包摘要和模板基线用于内部追溯，不要求用户再维护第三套版本号。兼容范围必须通过声明和测试确定，不能根据产品版本大小推断。

产品版本建议规则：

- `1.1.0-beta.1 -> 1.1.0`：同一目标版本从预览转正式，发布一个新的正式包，保留原 beta 包。
- `1.1.0 -> 1.1.1`：兼容性修复；若修复本身涉及项目格式变化，仍要单独评估迁移。
- `1.1.x -> 1.2.0`：新增兼容能力，例如统一升级入口和可选的文档更新能力。
- `1.x -> 2.0.0`：移除受支持接口、改变既有契约且不能兼容处理的变化。
- beta 用于需要试用反馈的阶段；rc 只在需要正式候选验收时使用，不机械增加发布步骤。

正式版不用继续叫 beta，也不用因为去掉 beta 而跳到 1.2.0。已发布版本、标签和资产不可原地换内容；不同内容需要新版本。构建元数据不能用来绕过同版本不同内容的保护。

**结构版本的具体安排：**

- 1.1.0 沿用 v6，前提是项目模板协议和强制规则保持兼容且不变化。
- 后续若引入必须由项目保存的模板基线、受管理区块和新的强制升级规则，按现有项目规范升级为 v7，并提供 v6 -> v7 迁移。
- 单纯发布脚本、安装下载或普通说明文字修正，不自动要求所有项目迁移。
- v7 不等于产品 7.0.0，也不自动意味着产品必须升级为 2.0.0；要看既有使用契约是否得到兼容支持。

### 3.2 稳定版与预览版

默认选择稳定渠道；只有明确选择预览渠道时才纳入预发布版本。渠道、精确版本和来源在计划中可见。

- “最新版”必须明确为某个渠道的最新已发布版本，不能用 main 的最新提交代替。
- 已安装预览版时，不静默永久订阅所有未来预览版本；首次需要选择渠道且无法从已有配置确定时，询问一次并保存偏好。
- 若已安装 1.2.0-beta.1，而稳定渠道只有 1.1.0，显示“当前安装领先于稳定渠道，保持现状”，不自动降级。
- 若同一目标的 1.2.0 正式版已发布，可从 1.2.0-beta.1 更新到 1.2.0。
- 离线、网络失败或缓存过期时，显示来源与核验时间；不能把“查不到新版”报告为“已经最新”。

远端发布记录的版本、预发布标志、资产摘要和包内版本必须一致。候选列表使用版本比较，不能按字符串、上传时间或分支名猜版本顺序。

### 3.3 兼容声明

发行元数据区分“可识别的历史结构”“可正常读写的结构”“可迁移到的结构”。识别 v1 并能迁移，不代表可直接用新写入器操作任意 v1 数据。

涉及任务状态或关联数据库时，分别检查其格式兼容性。仅更新工具不得隐式迁移关联数据库、开启关联能力或更新其他项目。

新写入入口应集中做兼容检查；未知或未来结构只允许有明确定义的诊断操作，写入必须拒绝。旧版本程序无法被新程序完全控制，切换前停止旧写入的要求仍需保留。

### 3.4 分支与发布关系

建议 main 作为通过检查的集成主线，允许包含下一版本的开发内容；用户安装稳定版以正式标签和发行包为准。这样既能保留当前已合入 beta 的事实，也能避免将每次 main 提交都当成新正式版本。

- 日常改动按需要使用短期 `feat-*`、`fix-*`、`chore-*` 分支，合并前通过对应检查；实际创建或切换分支仍在具体开发授权范围内。
- 预览与正式包都从明确提交构建，分别使用产品版本标签，例如 `v1.2.0-beta.1` 与 `v1.2.0`。
- main 的 README 明确区分本分支开发状态与最新稳定发行入口，历史版本文档随标签保留。
- 若 main 已包含 1.2.0 的新功能而 1.1.0 需要紧急修复，从 1.1.0 发布点制作 1.1.1 候选，再将修复同步回主线；不把未验收的新功能顺带放入修复版本。
- 不预设永久实验分支，也不维护多套同名安装目录；只有存在明确的旧版本维护需求时才保留对应维护分支。

## 4. 单一版本来源与发行流程

### 4.1 信息归属

| 信息 | 建议权威来源 | 生成或读取方式 |
| --- | --- | --- |
| 产品版本 | 仓库根 VERSION | 构建器唯一读取；包内保留对应值 |
| 目标结构版本 | 内置模板 WORKFLOW_VERSION | 构建和迁移器读取，不另外硬编码当前值 |
| 包内容 | release-manifest.json | 构建时生成文件集合、大小和摘要 |
| 兼容范围、源码提交、构建来源 | 发行信息文件 | 从版本输入、兼容配置和已提交源码生成 |
| 发布变化 | CHANGELOG.md | 维护面向用户的变化与升级影响 |
| 当前展示版本和下载入口 | 发布记录及其派生文档 | 自动生成或检查少量明确的展示位置 |
| 旧发布记录、任务和验收证据 | 原历史文件 | 保留当时的版本，不批量替换 |

“单一来源”指人工只维护一处产品版本，其他位置可以出现派生值，并由检查保证一致；不要求文档和 manifest 完全不出现版本号。

当前 manifest v1 严格限制字段集合。第一阶段优先维持其协议，把新增发行信息作为普通交付文件纳入哈希清单；如以后确需改变 manifest 协议，应增加显式协议迁移和旧包兼容测试，不能直接塞入字段使旧校验器失效。

版本集中后还要验证包脱离源码仓库能独立运行。构建器不能在安装后仍依赖仓库根 VERSION。校验旧包必须读取被校验包自己的版本，而非拿工具当前版本替代。

测试里描述当前构建结果的断言读取版本输入；描述历史升级、降级和预发布排序的固定版本样例继续保留。

### 4.2 发布流程

建议形成一条可复跑的维护流程：

`发布计划 -> 准备版本与说明 -> 固定候选提交 -> 构建与验证 -> 发布 -> 下载读回核验 -> 可选安装`

1. 发布计划列明目标版本、变更范围、兼容范围、结构是否变化、文档及验证清单。
2. 准备过程更新 VERSION、变更记录和必要的当前展示信息；不改历史版本文字。
3. 候选包从精确的已提交源码构建；发行目录放在仓库外，正式发布拒绝未说明的脏源码输入。
4. 生成完整压缩包、manifest、校验摘要、源码追溯信息和用户发布说明。验证独立解压安装、升级、恢复和可重复构建。
5. 在明确的发布授权下建立不可覆盖的版本标签与 Release。预览标记和版本后缀必须匹配，稳定入口只在稳定包验证通过后更新。
6. 下载实际发布的资产重新校验，核对标签、提交、包版本、结构版本和摘要；“上传成功”不能替代这一步。
7. 本机安装是后续独立操作。安装完成后再报告本机版本；发版本身不能被描述为本机已经更新。

发布中断时按已存在的标签和资产续接。已有内容一致则复用；不一致则停止，不能强制移动已发布标签或覆盖资产。保留旧稳定版入口，直到新稳定包完成核验。

第一阶段固定组合构建入口并明确其职责，避免一边转正式一边移动大量文件。生产源码收拢放到后续独立变更中，以运行包差异核对和回归验证，保留实验历史。

## 5. 用户升级体验与统一入口

保持自然语言入口，底层提供可脚本化的统一编排器。下列是目标行为，不是已经存在的新命令。

| 用户请求 | 处理范围 |
| --- | --- |
| 检查版本或查看升级计划 | 只读检查安装、来源及指定项目，不更新 |
| 更新 agent-workflow | 更新本机工具；不自动迁移所有项目 |
| 升级当前项目工作流 | 检查当前工具能否完成目标迁移；若必须更新工具且请求未覆盖该范围，说明必要变更后确认 |
| 更新工具并升级当前项目 | 在已授权范围内连续完成两步，分别报告结果 |
| 升级指定多个项目 | 固定项目清单，各项目独立预检、执行与恢复 |

含糊的“全部升级”需要确认对象范围；明确的请求不重复索要相同授权。发现真正的文档冲突、大幅改写 AGENTS.md 或需要扩大范围时，先给具体差异和原因。工作区外安装仍遵守实际工具权限。

统一入口应完成：

1. 识别安装位置、版本、完整性、来源与已选渠道；只检查用户指定的项目。
2. 解析远端候选或用户指定的本地包，下载到临时目录并验证。
3. 输出一份计划：安装变化、项目变化、文件差异、需处理事项、恢复点和最终目标。
4. 固定候选摘要与目标内容指纹。计划生成后内容变化则重新计划，不直接沿用旧授权中的旧差异。
5. 使用现有安装事务完成工具更新；在候选包中保留可独立调用的恢复入口。
6. 对范围内项目完成迁移、可自动完成的文档更新以及检查；只把无法确定的冲突交给用户。
7. 输出简短的结果和可恢复事务信息。

包下载限定在明确配置的发布来源，校验压缩包路径、文件类型、大小和摘要，保留离线包入口。哈希验证证明内容一致，不等于发布者身份签名；第一阶段使用明确的发布渠道，签名能力可以独立增强。

工具更新成功、项目升级失败时，报告两个真实结果，不自动把工具退回旧版，因为项目可能已发生合法的新格式变更。多个项目也采用各自事务，不能为了假装全局成功而覆盖已经更新的项目。

## 6. 项目文档与迁移机制

### 6.1 文档归属

| 内容类型 | 例子 | 更新方式 |
| --- | --- | --- |
| 工具维护的模板内容 | 通用工作流规则、入口引用 | 有明确基线时自动更新未定制内容 |
| 用户维护的项目内容 | 项目架构、命令、业务约束、偏好 | 保留，不用发行模板覆盖 |
| 混合文件 | AGENTS.md、工作流 README | 只维护有身份与基线的工具区块 |
| 历史事实 | 工作项、活动、验收和发布记录 | 不因工具版本更新改写 |
| 来源不明的旧内容 | 无基线的旧规则或人工定制文件 | 识别来源或先完成一次明确的归属审阅 |

文件路径本身不足以证明归属。现有 00-core 等文件也可能被用户修改，不能直接把整目录声明为工具所有。

新初始化项目使用短入口与明确的受管理区块，避免把相同规则大段复制到多个文件。既有项目通过一次可审阅的迁移接入，不强制重写全部历史文件。

### 6.2 基线与合并

项目保存已采用模板的身份、对应内容摘要、受管理区块和必要的基线文本。基线应能在离线环境重建；不能只保存一个无法取得原文的哈希。基线不是用户的全部项目快照，也不包含工作项历史数据。

比较三个对象：旧模板 B、当前本地内容 L、目标模板 T。

- L 与 B 相同：可直接应用 T。
- T 与 B 相同：保留 L，无需改动。
- L 与 T 相同：不重复修改。
- 双方都有变化：对有明确归属的模板文本或区块进行三方合并；有内容冲突则保留现场并生成精确差异。
- 项目约束与新版强制规则即使没有文本冲突，也要经过规则检查或 Agent 审阅；不能把文本合并成功当成语义兼容。

无基线旧项目：先尝试用可信历史模板和摘要识别；无法识别时保留为用户内容，生成最小增量方案。不得把未知本地内容偷偷当作“原始模板”，否则后续升级无法正确区分定制。

允许明确保留用户定制，并记录对应覆盖决定及适用模板；只有兼容检查通过才能结束。出现新的目标规则变化时重新判断，不能用一次“忽略”永远屏蔽未来冲突。完成的建议需归档或清理其活动状态，不能无限重复生成。

建议新增的项目元数据与本地事务目录须分别管理：可追溯的模板身份随项目保存；事务备份留在本地，不进入普通任务扫描、活动汇总或发布包。新增忽略规则、目录和强制协议都必须进入升级计划，按需要纳入 v7。

### 6.3 显式迁移步骤

每一步迁移定义来源结构、目标结构、前置条件、写入路径、完成检查、幂等行为和恢复要求。

现有 v1 至 v6 逻辑作为经过现有测试覆盖的历史适配器保留；不要为了形式整齐而重新虚构一套历史步骤。输出应说明使用历史适配器直达 v6，随后再执行新的 v6 -> v7 步骤。

迁移继续保留既有能力选择，不自动启用所有可选模块；任务状态冲突需要基于原始事实处理，未知历史日期保持未知，迁移不能顺便重算任务生命周期。

结构标记只在对应格式变更通过检查后推进；整体升级结果还要检查文档和任务状态，不能只看 WORKFLOW_VERSION。升级与修复现有项目缺失项也应在计划中分别展示。

## 7. 恢复、并发与完成状态

### 7.1 项目事务

为项目升级增加：计划指纹、固定写集、原文件备份、新建文件清单、逐步事务日志和恢复检查。只备份计划影响的文件及必要一致性数据，不备份或还原整个业务仓库。

- 预检后建立项目升级锁；所有新版本的任务、活动和其他项目写入器遵守同一维护边界，不能只让两个升级进程互斥。
- 统一规定安装锁、项目维护锁和工作项锁的取得顺序，避免死锁；多个项目逐个处理。
- 写入前后检查计划指纹，并使用原子替换和持久化日志。
- 中断后先识别事务状态，再决定继续或恢复，重复执行不重复迁移状态、不重写历史日期。
- 恢复只触及该事务写入的路径；新建文件仅在仍与事务结果一致时删除，旧文件仅在没有后续修改时恢复。
- 升级后出现新任务或用户编辑时，拒绝用旧快照覆盖，展示具体冲突。
- 外部编辑器和旧版写入器不一定遵守新锁；指纹可发现部分竞态，但不能据此宣称任意并发写入均安全。

运行包回滚与项目恢复保持分离。要回退项目格式，必须存在经过验证的逆向迁移或满足恢复快照条件；不能因为运行包可以回滚就宣布项目可无损降级。

### 7.2 对外结果

用户默认只看安装结果、当前项目结果和必要下一步；详细状态保留给诊断与自动化。

| 结果 | 含义 |
| --- | --- |
| 无需更新 | 在明确来源和范围内检查通过，无需执行 |
| 已完成 | 本次授权范围内的适用步骤全部完成并验证 |
| 待处理 | 有具体文档或选择事项，尚不能宣布完成 |
| 已阻断 | 兼容、状态、来源或内容冲突，未继续执行相关步骤 |
| 需要恢复 | 有未完成事务，需要先继续或恢复 |
| 执行失败 | 操作失败，并明确哪些已完成、是否已经恢复 |

同时保留安装和各项目的分项结果。没有纳入范围的项目显示“未检查”，不显示“全部最新”。已经成功的事务和整个请求完成是两个概念。

新增统一执行入口建议使用明确退出语义：0 表示本次执行目标完成或无需更新，2 表示待处理，3 表示预检阻断，4 表示执行失败或需要恢复。只读查询成功的退出码与其查询出的升级状态分开。

现有 CLI、JSON 字段和退出码先保留，通过兼容适配提供新结果；不直接改变旧脚本约定。旧调用方可以逐步迁移到新接口或显式的严格完成检查选项。

## 8. 公开文档与源码整理

### 8.1 文档职责

| 文档 | 面向读者的内容 |
| --- | --- |
| README.md | 产品用途、主要能力、快速开始、安装更新和文档入口 |
| CHANGELOG.md | 各已发布版本的变化、修复、兼容影响和必要迁移说明 |
| 使用与升级指南 | 稳定/预览渠道、更新范围、常见冲突与恢复办法 |
| 维护者发布指南 | 版本规则、候选准备、验证、发布和失败续接 |
| 开发记录 | 本机核验、备份位置、工作项、测试原始证据与内部讨论 |

README 不再承载“用户已确认”“本轮已完成”“本机路径”和内部权限说明。影响公开使用的兼容限制、停止旧写入要求和恢复边界仍需保留，以普通使用者能理解的语言说明。

CHANGELOG 的历史条目保留当时事实；后续主线采用或正式发布另记事件，避免将历史“尚未合并”误写成当前状态。当前版本信息集中展示，操作示例尽量使用变量与稳定入口。

### 8.2 源码整理

后续将稳定的多项目运行模块、统一 Skill 入口和发行工具移入正式源码布局；experiments 保留研究材料和可复现的历史证据。

迁移前先明确每个交付文件的唯一来源，删除重复来源前验证引用、导入、测试和构建路径。保留必要的旧命令兼容包装，并给出弃用周期。该工作独立验收，避免目录移动掩盖升级行为变化。

## 9. 分阶段实施与验收

| 阶段 | 主要交付 | 完成条件 | 依赖 |
| --- | --- | --- | --- |
| A：发布基础 | VERSION、发行信息生成、一致性检查、公开文档整理、基础 CI | 版本只人工维护一处；旧包可校验；构建和说明一致 | 本方案定稿 |
| B：1.1.0 正式收口 | 精确候选、独立包、发布说明、发布与读回流程 | 当前能力回归通过；beta -> 正式更新和恢复通过；发布资产读回一致 | A |
| C：统一升级编排 | 来源/渠道选择、本地包入口、固定计划、统一结果 | 一次明确请求可完成安装更新及所选项目流程；不改未选项目 | A；按新预览版交付 |
| D：项目升级引擎 | 模板基线、文档归属、增量合并、迁移步骤、项目事务 | 保留用户修改；旧项目可接入；中断和恢复场景通过 | C；预计需要 v7 |
| E：1.2.0 验收与正式发布 | 预览反馈修复、真实副本试跑、有限范围升级、完整文档 | 升级体验及保护条件均达标，再按已建立流程转正式 | C、D |
| F：源码整理与维护扩展 | 正式模块布局、兼容包装、可选签名和批量体验改进 | 包和用户行为符合约定，独立通过回归 | 核心流程稳定后 |

建议第一轮先完成 A、B，让已经认可的能力有一个清晰的正式版本。C、D 应进入 1.2.0-beta.1 等预览版本，不以“改个名称”的方式跳过验证。预览编号按实际交付递增；rc 按需要安排。

每个阶段拆成可单独审查、可验证的小变更：

1. 版本来源与包独立性。
2. 文档职责和一致性检查。
3. 发行准备与发布自动化。
4. 升级计划及整体结果模型。
5. 渠道解析、下载与安装适配。
6. 文档归属、基线和旧项目接入。
7. 项目事务与所有相关写入口的协调。
8. 迁移适配、集成验证和用户指南。

阶段 A、B 不依赖新项目迁移引擎；阶段 D 的整体收口必须依赖项目事务与并发保护，不能先放开自动合并再补保护。

## 10. 验证矩阵

以下是后续实施验收要求，不是本轮已通过的测试。

| 场景 | 必须证明的结果 |
| --- | --- |
| 从 1.1.0-beta.1 升到 1.1.0 | 包版本更新正确；现有 v6 项目无需因去掉 beta 改写 |
| 相同版本、相同内容 | 重复执行无需更新，不产生重复事务 |
| 相同版本、不同内容 | 明确拒绝覆盖 |
| 预览安装切稳定渠道 | 不降级；对应正式版出现后可正常前进 |
| 无 manifest 的旧安装 | 明确旧来源未知，完整备份后更新，不猜版本 |
| 新版工具校验历史包 | 不要求历史包包含后来新增的运行模块或元数据 |
| 包离开源码目录独立执行 | 校验、更新、恢复不依赖开发仓库或网络 |
| 断网、资产不全、摘要不匹配 | 不修改现有安装；明确失败或信息缺口 |
| 未修改的模板和混合入口 | 自动更新受管理部分，用户正文保持不变 |
| 用户定制与新版无冲突 | 合并后保留定制，验证新增规则已生效 |
| 文本或规则冲突 | 精确显示差异，不覆盖，不宣布完成 |
| 没有模板基线的旧项目 | 先识别或审阅接入，不能假造基线 |
| 历史 v1 至 v6 与未来结构 | 已支持路径可迁移；未知和未来结构拒绝写入 |
| 状态已迁移但旧正文不同 | 保护 .state.json 当前事实，不用旧正文回退任务 |
| 已启用/未启用的可选能力 | 保留原选择，不自动扩展目录或关联网络 |
| 计划后文件变化 | 旧计划失效并重新检查 |
| 两个升级者及任务写入竞争 | 同一新协议内正确互斥，不丢活动或任务状态 |
| 安装与项目各提交边界中断 | 可明确继续或恢复；重试不重复写事实 |
| 升级后用户又编辑或新增任务 | 恢复不覆盖后续修改，不删除新增任务 |
| 一份安装对应多个项目 | 仅修改明确选择的项目，失败结果逐项报告 |
| 旧命令与新编排器 | 已有调用保持兼容，新接口有确定的完成语义 |
| README、包、标签与发布记录 | 当前信息一致，历史记录保留原版本 |

代码变更执行项目规定的测试与编译检查，并覆盖最终生成的发行包，而非只测源码。运行 macOS/Linux 和声明支持的 Python 版本矩阵；未执行的环境明确列为未验证，不能用跳过测试代替通过。

真实验证顺序：隔离样例 -> 脱敏项目副本 -> 当前项目 -> 明确选择的实际项目。现有使用认可证明的是已交付能力；新升级路径、恢复和文档合并需要新的证据。

## 11. 本次落地时的具体处理

- **现有 beta：** 保留原包和历史，不重打同版本包覆盖安装。
- **正式版：** 生成新的 1.1.0 包，沿用已验证功能；发行工具与说明变化要按差异重新验证，不宣称新旧包逐字节一致。
- **本机安装：** 发布后按单独的安装范围更新，完成后读回版本、清单与来源。仍安装 beta 但与 beta 原包一致，应如实报告，不称为安装损坏。
- **当前仓库 v5：** 可在明确安排的项目升级中进入 v6；现有计划是补一份规则文件、更新结构标记、处理三份入口文档，没有任务状态迁移冲突。不能把该项目升级当成正式发版的必然副作用。
- **其他 v6 项目：** beta 转 1.1.0 不要求重新初始化或批量改版本文字；以后启用 v7 时再分别规划。
- **已有 v5 备份：** 保留原标签和压缩包。v5 备份是旧源码恢复点，不作为当前运行包或项目数据可直接回退的证明；今后发行使用产品版本标签，结构号只用于结构说明。
- **公开 README：** 按本方案重新组织当前使用说明；内部切换记录继续留在开发记录，不混入快速开始。

## 12. 范围与后续决策

本方案覆盖发布规则、版本来源、公开文档、安装更新、项目迁移、完成状态、恢复和验证。当前不安排云端服务、后台自动更新、跨机器同步或多项目统一回滚。

建议采用的默认选择已经明确：正式目标 1.1.0、稳定渠道优先、产品与结构版本分离、统一编排而保留底层命令、只在有归属和基线的范围自动合并、升级体验通过后续预览版迭代。

实施时再根据结果确定两项：新项目协议是否确实需要 v7；兼容旧接口后 1.2.0 是否足以表达变更范围。如果最终需要打破既有契约，应调整版本计划，而不是为了保留预定版本号隐瞒不兼容。

方案形成后，用户已授权第一批本地开发与候选验证。正式发布、本机安装、具体项目迁移及后续升级引擎仍按各自明确的任务范围推进；第一批开发不表示这些操作已经执行。
